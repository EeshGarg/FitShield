# 0.57 — Less machinery behind the same product

*2026-09-22*

Upgrading from 0.56 should feel like nothing happened. Every feature is still
here, the screens are unchanged, and the product still does exactly what it did.
Underneath, FitShield does considerably less work to do it, several things that
were quietly duplicated are now written once, and Apple/Safari support — which
could not be developed or tested without hardware nobody here has — is gone
rather than sitting in the tree pretending to be maintained.

This is the last release before 1.0, and the point of it was to stop carrying
things that were not earning their place.

## Apple and Safari are gone

FitShield targets Chromium browsers, Firefox and Android. The Safari build was
experimental, needed macOS and Xcode to finish, and could never be verified on
the hardware it targeted. It has been removed completely: the build target, the
converter tooling, the macOS CI job, the installer script, the audit, the
Safari-only test, and the documentation implying current support. Eighteen
validators run now instead of nineteen, and `node build.js` produces exactly two
packages.

Old release notes still mention Safari, because they were accurate when written.
Nothing in them has been rewritten.

One thing was kept rather than deleted. The Safari audit scanned the shipped
package for APIs Safari lacks — among them `chrome.gcm`, `chrome.identity` and
`chrome.system`. Framed as a Safari concern that check was disposable; framed
honestly it is a permissions-and-privacy check that matters on every browser,
because those APIs would contradict the three permissions FitShield declares and
the promise that it makes no network calls. It now lives in the extension audit,
with each API carrying the reason it is refused.

## Work the extension stopped doing

Every one of these was measured, and none of them changes what you see.

- **A worker wake-up no longer parses the catalog to discover it has nothing to
  do.** Bringing storage up to date was gated behind loading 814 KB of blocklist
  JSON and reading the entire profile — on every service-worker generation, on
  the entry path of recording an interruption, and therefore while a block page
  was already counting down. It now reads the schema stamp first. An up-to-date
  profile records an interruption with no dataset load at all.
- **Dragging the pause-length slider no longer rebuilds the blocking rules.**
  `timerSeconds` and `passDurationMinutes` were treated as inputs to the rule
  set. They are not. One drag queued dozens of full teardowns and rewrites of
  about 2,500 `declarativeNetRequest` rules.
- **An unchanged rule set is no longer rewritten.** Every refresh replaced all
  2,500 rules even when the result was identical, and the browser persists and
  re-indexes on every such call.
- **One user action queues one refresh.** Granting a pass wrote the pass and then
  asked for a refresh, while the write itself had already asked for one.
- **Country and category policy is evaluated once per pass, not once per brand.**
  Testing the catalog built a fresh code set for every entry — about 10,000
  short-lived sets per refresh. The engine now exposes the hoisted form; the
  answers are identical for all 2,505 entries, and the pass is 8× faster.
- **The block-page redirect URL is built once instead of 2,500 times.**
- **Settings stops building rows nobody can see.** Both site lists start
  collapsed, and both were being built anyway — about 25,000 DOM nodes created
  into hidden containers, on load and again on every save.
- **The popup stops re-filtering 2,505 sites every second** to re-derive counts
  that cannot change until the state object is replaced.
- **Currency names and symbols are memoized.** Opening the currency picker built
  about 135 `Intl` objects; a language change built them all again.
- **The animated background repaints when its time of day actually changes**
  rather than every twelve minutes. Its own comment always said that was the
  intent; 116 of the 120 daily repaints were replacing the field with freshly
  randomized colors and restarting every animation mid-flight.
- Plus smaller ones: the stats maps that a block writes are now only the ones
  that moved, a one-time legacy repair stops re-checking storage forever, and the
  pass list is not written back when it has not changed.

## Work Android stopped doing

The dashboard polls permission states every two seconds because Android offers no
change event for them. That poll is still there, and still every two seconds —
but it now stops while the app is not on screen, which it never did, and each
tick costs less than half what it did.

- The poll is skipped entirely when the app is backgrounded. Returning to the app
  refreshes the whole dashboard, not just the permission rows — which is what the
  resume handler should always have done.
- Two values that cannot change while the process lives — the app version and the
  host count — are no longer fetched across the bridge every two seconds. One of
  them was a `PackageManager` round trip.
- The status card and the most-blocked lists are only rewritten when their
  contents differ. The lists were rebuilding about 60 nodes every two seconds
  whether or not anything had changed.
- Reading several stored values now costs one bridge crossing instead of one per
  key: nine down to one for the app-blocking panel, five down to one for stats.
- The recipe search stopped re-deriving its haystack on every keystroke, and the
  card tilt stopped forcing a layout flush on every touch sample.
- The block screen no longer loads the 85-entry language list it never used.

Net effect: about fourteen bridge crossings per visible tick became eight, and
zero while the app is in the background.

## Things that were wrong

- **Android honored a pause length it did not accept.** The dashboard took any
  number of seconds from 10 upward with no maximum, stored it, and then counted
  down at most 300. Both sides now agree on the 10–900 range the product states,
  the missing maxima are on the inputs, and a typed `0` clamps to the minimum
  instead of silently becoming the default.
- **Android dropped the largest category from "most blocked".** The check that
  excludes internal rule buckets still had its pre-fix form on the Android side,
  and it discarded `delivery` — 373 of the 2,512 hosts, and a category the picker
  offers. Both platforms write the same stored counter, so one of them was
  corrupting it. The exclusion now happens where the value is derived, and the
  Android code carries no category vocabulary at all.
- **"Open anyway" did not cover a brand's other domains.** The unlock was stored
  against the brand but looked up by the exact host, so for the four shipped
  brands with alias domains the user was re-blocked on the very site they had
  just been let through. Fixed by carrying the brand with the host in the
  generated data rather than by inferring it.
- **A custom site that was not a domain was confirmed as blocked.** Typing
  `doordash` or `.com` produced a rule that could never match while Settings
  said "Added to blocklist", and a trailing dot produced a rule that could never
  match either. There were three different validators for this — the worker, the
  Settings page, and the one in the shared core that the other two overrode. Now
  there is one, and it is the strict one; the offline fallback also stops losing
  custom sites saved in the historical format.
- **Typing a pause length by hand could disagree with the label above it.** The
  friction profile shown ("Light", "Standard", "Strict", "Custom") was derived by
  comparing two of the six values a preset writes, so turning "Ask what brought
  me here" off left the label reading "Standard". Three pages had each written
  their own stricter copy to work around it. The shared one is now correct and
  the three copies are gone.
- **Android normalized a typed hostname differently from the engine.** A pasted
  URL, a `host:443`, or a trailing dot in the Android allow list or custom list
  produced an entry that could never match. Both now follow the same algorithm,
  checked by running the compiled Kotlin and the engine over the same 27 inputs.
- **The Play listing described two Android defects that had already been fixed.**
  It said the Alternatives panel shows the first 24 of 88 entries and prints
  `[object Object]`, and a screenshot instruction told whoever takes the shots to
  hold that one. Both were fixed earlier; the test that should have caught the
  stale claim was matching the comments left behind explaining the fixes.

## One implementation instead of several

- The service worker no longer carries its own copy of the site-record and key
  logic that the Settings page loads as a module. The keys the page writes are
  the keys the worker reads, so the two were kept byte-identical by hand with a
  test to prove it. There is one copy now.
- The list of storage keys that make up "the settings" lived in two places: a
  hand-maintained copy in the worker, which had drifted, and nowhere at all in
  the preferences panel, which read the entire profile instead — including three
  unbounded lifetime counters — on every save. It lives in the core now, with a
  test that fails if it stops matching what the reader actually reads.
- The Android country namer was replaced by the shared one, so a country reads
  the same on the phone as in the browser.
- The Android asset-copy list is no longer duplicated between the bundler and the
  audit that checks it, and that audit now compares every field of the generated
  rules asset rather than only the host list and its hash.
- A duplicate 128px icon, a dead currency helper, an unreleased pass-preset
  compatibility branch, and four spent work-queue files were removed. The last of
  those would have failed the validators with 58 errors the next time a queue was
  written.

## A test that could not fail

One test claimed that if the language picker gained a seventh right-to-left
language it would fail until the code was taught about it. It read a property the
module does not export and then filtered on a key the options do not have, so the
list it checked was always empty. It now reads the real picker and holds it and
the code to each other in both directions.

## What did not get smaller

Package size went slightly **up**: the Chrome archive from 732,062 to 742,371
bytes, and the production JavaScript from 519,952 to 548,163. Line count went up
too. The reductions are real — Safari tooling, the duplicated implementations
above — but they were outweighed by comments explaining why the cheap path is
equivalent to the expensive one it replaced, by the small caches that make it
cheap, and by new tests that execute behavior rather than grep for it.

That is the trade this release made deliberately. Less work at runtime, more
explanation in the source. The alternative — the same speed-ups with no record of
why they are safe — is how a later reader "simplifies" a cache back into a hot
loop.

## The catalog did not change

Stated rather than skipped, because release notes that go quiet about the catalog
are how a stale number survives. Everything below is what 0.56 shipped, recounted
from the data for this release:

**2,505 curated brands across 111 markets**, split 514 delivery platforms and
1,991 fast-food brands.

Every brand carries its real category from the blocklist: *Asian*, *Bakery*,
*Burger*, *Catering*, *Chicken*, *Coffee*, *Delivery*, *Dessert*, *Fast Casual*,
*Grocery*, *Korean Food*, *Meal Delivery*, *Meal Kit*, *Mexican*, *Pizza*,
*Restaurant*, *Restaurant Discovery*, *Sandwich*, *Seafood*, *Smoothie* and
*Tea* — the 21 categories the current data uses.

The four brands 0.56 re-checked by hand still interrupt, and were re-checked
again here rather than carried over on trust: **LINE MAN**, **EatFit**,
**Jumia Food** and **BHC Chicken**.

**88 alternatives** answer them — **46** full recipes and **42** quick fixes.
**68** are vegetarian or stricter and **20** of those vegan; **26** need no heat
at all, and **37** need no stove or oven.

No brand was added, removed or recategorized, and no alternative was edited. If
you had a site blocked in 0.56, it is blocked in 0.57.

## Compatibility

Chrome and other Chromium browsers, Firefox, and Android. Nothing about storage,
backups or migrations changed: a 0.56 profile carries straight over, and a
pre-0.55 profile still migrates. Still no telemetry, no accounts, no network
calls, no cloud, and the same three permissions — `storage`,
`declarativeNetRequest`, `alarms`.
