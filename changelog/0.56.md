# 0.56 — Contact with a real phone

*2026-08-26*

Every Android claim FitShield made came from unit tests, static analysis and
reasoning. None of it had run on hardware. This release is what happened when it
did: a Samsung Galaxy S24 Ultra on Android 16 / One UI 8.5, driven over ADB
through the nine checks in
[`docs/DEVICE_DEBUG_HANDOFF.md`](../docs/DEVICE_DEBUG_HANDOFF.md).

Seven things were wrong. Six of them were invisible to the entire test suite,
because they lived in the gap between "the logic is correct" and "the phone does
the right thing".

## The one that mattered most: unrelated sites broke without IPv6

FitShield routes `::/0` into its tunnel so that IPv6 is *filtered* rather than
quietly bypassing the filter. On a network with no working IPv6 that backfired.
The client's IPv6 attempt was accepted by the tunnel, the handshake completed
locally, the upstream connect then failed, and the connection was reset. Having
watched a connection **establish**, the browser reported the site as reset
instead of falling back to IPv4 — the fallback that takes milliseconds when
FitShield is off, because the connect fails immediately with no route.

On an IPv4-only Wi-Fi, with FitShield on, `en.wikipedia.org` gave *"This site
can't be reached. The connection was reset."* With FitShield off it loaded. A
blocker that breaks Wikipedia is worse than one that misses a delivery brand.

An IPv6 connection is now refused outright when IPv6 is known not to work, so the
client fails over exactly as it does with no VPN at all. The answer comes from
evidence — what FitShield's own protected upstream sockets actually do — not from
asking the system, which reported IPv6 as available because an idle cellular
network still advertised a global address and a `::/0` route while the Wi-Fi
carrying every packet had neither. `::/0` stays routed, so the moment a network
really carries IPv6 it is filtered again.

## Two controls that did nothing

Both were stored, listed back with a Remove button, and never consulted by the
filter, because the matcher read only the packaged rules asset:

- **Always-allow domains**, which the app describes as "domains here are never
  blocked". A domain sitting in that list was still reset.
- **Custom URLs**. A domain typed in was never blocked.

Both now reach the matcher, and live — the service watches its preferences, so a
change applies without restarting the tunnel. An allow entry wins over both the
curated set and the user's own additions.

## The pause screen

- **The countdown restarted on every rotation.** The block screen declared no
  `configChanges`, so Android destroyed and recreated it on each turn of the
  wrist, the WebView reloaded, and the timer began again from the top. Measured
  at 25s → 18s → rotate → 57s. The countdown is the intervention; resetting it by
  accident makes the wait unbounded and teaches the user the number is arbitrary.
- **"Open anyway" only unlocked half the app.** The temporary unlock bound the
  accessibility layer and not the connection filter, so a blocked app opened and
  then could not reach its own servers — and every retry added another
  interruption to the counter. An unlock the user deliberately chose now holds
  across both layers, and still expires on time.

## The launcher icon was clipped

The icon was generated to fit the 72dp mask **square**. That is the masked
viewport, not the safe zone: the launcher picks the mask's *shape*, and only the
centred **66dp circle** survives all of them. A letter F, taller than it is wide,
got its stem sliced flat by One UI's squircle. Ink now reaches 32.5dp from the
centre instead of 39.9dp.

The check that should have caught this compared the bounding box against the same
square it had just been fitted to, so it agreed with itself and never applied a
mask. It is now an assertion on the pixels of the generated file.

## Smaller, but wrong

- The restore notice said **"Your phone restarted"** after an app update, when
  the phone had not restarted. It now names the event that actually happened.
- The in-app note claiming timing enforcement "lands in a later step" was stale:
  the schedule and the timer both worked. The schedule now also covers site
  blocking, which it did not before — one switch had been giving two answers.
- Country and category selections are documented honestly. They cannot change
  what the connection filter blocks: the catalog is a union, the shipped asset
  already contains every curated delivery and fast-food brand, and those
  selections only ever *add*.

## Tests that can fail

Six of these seven were unreachable by the suite because they lived in classes
that need an Android `Context`. The pure decisions were pulled out into
`HostMatch`, `Schedule` and `BlockDecision`, which the Node suite compiles and
**executes**, so the tests now run the shipped logic instead of asserting on the
shape of its source. Every fix has a test that fails without it.

The Kotlin harness itself was broken and had been hiding behind a stale compile
cache: it chose the newest compiler and the newest stdlib independently, pairing
1.9.24 with 2.1.0, and died on any fresh compile. Versions are matched now.

## What this release blocks, and what it offers instead

Nothing in the catalog changed in 0.56 — the fixes above are about the phone, not
the data. It is restated here because these are the numbers a user's blocking
actually depends on, and a release that does not repeat them is a release nobody
can check.

**2,505 curated brands across 111 markets**, split 514 delivery platforms and
1,991 fast-food brands. On Android those reach the phone as 1,511 blockable app
packages alongside the connection filter's host rules.

Every brand carries its real category from the blocklist: *Asian*, *Bakery*,
*Burger*, *Catering*, *Chicken*, *Coffee*, *Delivery*, *Dessert*, *Fast Casual*,
*Grocery*, *Korean Food*, *Meal Delivery*, *Meal Kit*, *Mexican*, *Pizza*,
*Restaurant*, *Restaurant Discovery*, *Sandwich*, *Seafood*, *Smoothie* and
*Tea* — the 21 categories the current data uses.

The brands whose food arms survived 0.55's removal of non-ordering sites still
interrupt, and were re-checked here rather than assumed: **LINE MAN**,
**EatFit**, **Jumia Food** and **BHC Chicken**.

**88 alternatives** answer them — 46 full recipes and 42 quick fixes. 68 are
vegetarian or stricter, of which 20 are vegan; 26 need no heat at all and 37 need
no stove or oven. These are what the pause screen offers instead of an order, and
on this phone they rendered as real prose rather than the `[object Object]` a
synthetic DOM had been hiding.

## What this release does not claim

- **IPv6-only carriers are unverified.** Both networks available were dual-stack
  or IPv4-only, and this was not inferred from dual-stack working.
- **Deep Doze over hours is unverified.** A phone on the ADB cable is charging,
  and One UI refuses the AOSP `deviceidle` stepping that exists to work around
  that. A 25-minute screen-off soak passed with the service alive and filtering.
